## Процесс работы: GitHub Flow

В репозитории одна основная ветка — `main`. В ней всегда лежит рабочая версия проекта.
Напрямую в `main` коммитить нельзя (ветка защищена), все изменения попадают туда только через Pull Request.

Порядок работы над задачей:

1. Возьмите Issue на доске [Project](https://github.com/orgs/study-ai-assistant/projects/1): назначьте себя исполнителем и переведите карточку в статус **In Progress**.
2. Обновите локальную `main`:
   ```bash
   git switch main
   git pull
   ```
3. Создайте короткую ветку под задачу:
   ```bash
   git switch -c feature/12-upload-screen
   ```
4. Делайте небольшие коммиты по ходу работы и регулярно отправляйте ветку на GitHub:
   ```bash
   git push -u origin feature/12-upload-screen
   ```
5. Откройте Pull Request в `main`, заполните шаблон, переведите карточку в **In Review**.
6. Исправьте замечания ревьюера, дождитесь одобрения.
7. Влейте PR (кнопка **Squash and merge**) и удалите ветку. Issue закроется автоматически благодаря `Closes #N`.

Ветка живёт недолго: в идеале 1–2 дня. Если задача не помещается — разбейте её на несколько Issue.

## Именование веток

Формат: `<тип>/<номер-issue>-<кратко-латиницей>`

| Тип | Когда использовать | Пример |
|---|---|---|
| `feature/` | новая функциональность | `feature/12-upload-screen` |
| `fix/` | исправление ошибки | `fix/31-empty-result-crash` |
| `docs/` | только документация | `docs/7-contributing-update` |
| `chore/` | настройка, зависимости, CI | `chore/5-ci-lint` |

Правила: только латиница в нижнем регистре, слова через дефис, без пробелов.

## Формат коммитов

Используем [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/). Сообщение пишем на русском.

```
<тип>: <что сделано, в повелительном наклонении>
```

| Тип | Значение |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление ошибки |
| `docs` | документация |
| `style` | форматирование, без изменения логики |
| `refactor` | переработка кода без изменения поведения |
| `test` | тесты |
| `chore` | настройка, зависимости, служебные изменения |
| `ci` | настройка CI |

Примеры:

```
feat: добавить экран выбора режима обработки
fix: исправить падение при пустом ответе сервера
docs: описать запуск сервера в wiki
```

Плохие примеры: `fix`, `правки`, `asdf`, `WIP`.

## Pull Request

- **Маленький.** Один PR — одна задача. Ориентир: до 300–400 изменённых строк. Большой PR сложно проверить.
- **Связан с Issue.** В описании обязательно `Closes #N` (номер Issue из этого репозитория). Для Issue из другого репозитория: `Closes study-ai-assistant/<repo>#N`.
- **Заполнен шаблон.** Что сделано, как проверить, отмечен чек-лист Definition of Done.
- **Минимум одно одобрение** (approve) от другого участника. Своё одобрение не считается.
- **Никаких секретов.** Репозитории публичные: ключи API, токены, пароли и личные данные в коде, коммитах и PR запрещены. Настройки — только через переменные окружения, пример — в `.env.example` с пустыми значениями.
- Если PR ещё не готов, но хотите показать — откройте его как **Draft**.

## Code review

Review — это помощь, а не экзамен. Цель — чтобы в `main` попал понятный и рабочий код, а команда училась друг у друга.

### Как ревьюить

- Отвечайте на запрос review в течение рабочего дня.
- Комментируйте код, а не человека: «здесь можно упростить», а не «ты написал плохо».
- Объясняйте **почему**, предлагайте вариант исправления.
- Отмечайте мелочи префиксом `nit:` — они не блокируют слияние.
- Хвалите удачные решения.
- Не понимаете код — спросите. Это тоже полезный комментарий.

### Чек-лист ревьюера

- [ ] PR связан с Issue, критерии приёмки из Issue выполнены
- [ ] Изменения соответствуют задаче, нет лишнего
- [ ] Проект собирается и запускается (проверено локально или в CI)
- [ ] Код понятен: имена переменных и функций говорят сами за себя
- [ ] Нет секретов, ключей, паролей, личных данных
- [ ] Обработаны ошибки (например, сервер или LLM API недоступны)
- [ ] Есть тесты, если они применимы
- [ ] Документация обновлена, если поменялось поведение или запуск

### Как автору реагировать на review

- Отвечайте на каждый комментарий: исправили — напишите «исправлено», не согласны — объясните.
- Не принимайте замечания на свой счёт.
- После исправлений нажмите **Re-request review**.
