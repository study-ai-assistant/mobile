## Общая схема

Экраны → состояние и валидация → клиент API → сервер backend → LLM.
Ключ LLM хранится на сервере; приложение обращается только к backend.

## Экраны и переходы

| Экран | Назначение | Откуда открывается | Куда можно перейти | Состояния |
|---|---|---|---|---|
| Загрузка материала | Ввод учебного текста; выбор файла в следующем спринте | При запуске приложения; возврат с выбора режима | Выбор режима после проверки материала | Пустое поле, введённый материал, ошибка пустого/слишком большого текста; состояния загрузки файлов уточняются с design |
| Выбор режима | Выбрать краткий/подробный конспект, простое объяснение, вопросы для самопроверки или ключевые термины | Загрузка материала; повторная обработка с экрана результата | Назад к материалу; после отправки — ожидание и результат | Режим не выбран, режим выбран, отправка/ожидание, ошибка сервера, долгое ожидание |
| Результат | Показать результат выбранного режима | Успешная обработка с выбора режима | Назад к режимам с сохранением материала; новый материал — к загрузке | Успешный результат; ошибка/пустой ответ — сообщение с возможностью вернуться и повторить действие |

Ожидание и ошибки — состояния основных экранов, а не дополнительные обязательные
экраны. Повторная отправка выполняется только по действию пользователя.

## Спринт 1: технический экран

mobile#6 — отдельная проверка связи, объединяющая поле текста, кнопку «Отправить»
и область ответа на одном экране. Она не заменяет согласование трёх экранов выше.
Для проверки доступности предусмотрен `GET /health`. Обработка текста использует
планируемый `POST /api/v1/text/process` с режимом `SHORT_SUMMARY`.
Остальные четыре режима входят в целевой пользовательский сценарий, но пока не
поддерживаются обработчиком первого спринта. Загрузка PDF/DOCX — следующий спринт.
